# Deployment

Fuel's backend runs on **Render**, with **Neon** (Postgres), **Upstash** (Redis) and **Resend**
(email). Error tracking is **Sentry**. Everything is defined in [`render.yaml`](../../render.yaml)
at the repo root.

| Environment | Git branch | Render service | Plan |
|---|---|---|---|
| Staging | `dev` | `fuel-api-staging` | free (sleeps when idle) |
| Production | `main` | `fuel-api` | starter (always on) |

A merge into `dev` or `main` triggers the PR Checks workflow on the merge commit. Render deploys
that commit only once the checks pass (`autoDeployTrigger: checksPass`). Changes outside
`Fuel/backend/` (docs, the future mobile app) don't trigger a deploy.

**Region:** keep all three providers in the same region (Render `virginia`, Neon
`aws-us-east-1`, Upstash `us-east-1`). Every request talks to the database and Redis, so
cross-region latency adds up quickly.

---

## One-time setup

Do this once per environment (staging, then production).

### 1. Neon (Postgres)

1. Create a project in **AWS US East 1**. Use one Neon branch per environment (`staging`,
   `production`), or a separate project for production.
2. Turn on point-in-time restore (history retention) for the production branch.
3. Copy the **direct** connection string, **not** the pooled one (no `-pooler` in the host).
   Flyway's migration lock needs a direct session. Split it into:
   - `DATABASE_URL` = `jdbc:postgresql://<host>/<database>?sslmode=require`
   - `DATABASE_USERNAME`, `DATABASE_PASSWORD`

The schema is created by Flyway when the app first starts. Don't create tables by hand.

### 2. Upstash (Redis)

1. Create a **regional** Redis database in **us-east-1** (not Global).
2. `REDIS_HOST` = the endpoint host, `REDIS_PASSWORD` = the password. TLS and port come from the
   Blueprint (`REDIS_SSL=true`, `REDIS_PORT=6379`).

If Redis is unreachable the app keeps serving, but the rate limits are off (they fail open), so
treat a Redis outage as urgent.

### 3. Resend (email)

1. Add and verify your sending domain, then add the SPF, DKIM and DMARC records Resend shows to
   your DNS. Without them, verification emails go to spam. See [EMAIL_SETUP.md](EMAIL_SETUP.md).
2. Create an API key with sending access: `MAIL_PASSWORD`.
3. `MAIL_FROM` = an address on the verified domain, e.g. `no-reply@<your-domain>`.

The app connects to Resend at startup and refuses to start with wrong credentials.

### 4. Sentry (optional, recommended)

Create a Java project and copy its DSN into `SENTRY_DSN`. Without it, nothing is reported.

### 5. Render

1. In Render: **New → Blueprint**, pick this repo. Render reads `render.yaml` and asks for every
   variable marked `sync: false` (see the table below).
2. Generate `JWT_SECRET` for each environment (they must differ):

   ```bash
   openssl rand -base64 64
   ```

   `VERIFICATION_CODE_SECRET` is generated by Render.
3. Apply. The first deploy runs the Flyway migrations.
4. Optional: add a custom domain such as `api.<your-domain>` in the service settings; Render
   issues the TLS certificate.

## Environment variables

| Variable | Set by | Notes |
|---|---|---|
| `SPRING_PROFILES_ACTIVE` | Blueprint | `prod`: real SMTP, JSON logs, no Swagger |
| `APP_ENVIRONMENT` | Blueprint | `staging` / `production`; tags logs and Sentry events |
| `PORT` | Render | The app listens on it |
| `RENDER_GIT_COMMIT` | Render | Used as the Sentry release |
| `DATABASE_URL` | you | `jdbc:postgresql://<host>/<db>?sslmode=require`, direct (not pooled) |
| `DATABASE_USERNAME` / `DATABASE_PASSWORD` | you | Neon role |
| `REDIS_HOST` / `REDIS_PASSWORD` | you | Upstash |
| `REDIS_PORT` / `REDIS_SSL` | Blueprint | `6379` / `true` |
| `MAIL_HOST` / `MAIL_PORT` / `MAIL_USERNAME` | Blueprint | `smtp.resend.com` / `587` / `resend` |
| `MAIL_PASSWORD` | you | Resend API key |
| `MAIL_FROM` | you | Address on the verified domain |
| `JWT_SECRET` | you | `openssl rand -base64 64`; changing it signs everyone out |
| `VERIFICATION_CODE_SECRET` | Render (generated) | Changing it only invalidates codes in flight |
| `GOOGLE_CLIENT_IDS` | you | Comma-separated iOS/Android/web client IDs; see [OAUTH_SETUP.md](OAUTH_SETUP.md) |
| `APPLE_CLIENT_IDS` | you | iOS bundle ID / Services ID |
| `APPLE_TEAM_ID` / `APPLE_KEY_ID` / `APPLE_PRIVATE_KEY` | you, later | Needed before App Store submission (token revocation on account deletion); add in the dashboard |
| `USDA_API_KEY` | you | Free key from [api.data.gov](https://api.data.gov/signup/); without it `GET /api/food/search` returns 503. Add it in the Render dashboard |
| `SENTRY_DSN` | you | Optional |
| `JAVA_OPTS` | optional | Overrides the Dockerfile default `-XX:MaxRAMPercentage=70 -XX:+ExitOnOutOfMemoryError` |

Secrets live only in the Render dashboard. Never commit them, and never reuse the values from
your local `.env`.

## After each deploy

- Health: `GET /actuator/health/liveness` (Render's check) and `/actuator/health/readiness`
  (also checks the database; use it for uptime monitoring).
- Smoke test on staging: register → email arrives → verify → log in → refresh → log out →
  forgot/reset password → delete account.
- Check that the per-IP rate limit sees real client IPs: six quick logins from your machine
  should get `429` on the sixth, while another network is still allowed. If everyone shares one
  limit, the proxy's forwarded IP isn't trusted (`server.tomcat.remoteip.internal-proxies`).

## Rolling back

- **Code:** in the Render service, open **Events**, pick the last good deploy and choose
  **Rollback**. Then revert the bad commit on the branch, or the next push redeploys it.
- **Database:** migrations only move forward. To undo data damage, restore the Neon branch to a
  point in time before the deploy (Neon → Branches → Restore), and roll the code back with it.
